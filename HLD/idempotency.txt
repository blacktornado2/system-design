Idempotency:
 - An operation is "idempotent" if performing it multiple times has the SAME effect as performing it once.
 - Doesn't mean the response is identical every time — it means the end STATE of the system doesn't change after the first successful call.
 - Core problem it solves: network/client retries causing duplicate side effects (double charges, duplicate orders, duplicate emails, etc.)


# Why does this matter?
    Networks are unreliable. Classic failure scenario:
    1. Client sends "Charge $50" request.
    2. Server processes it, charges the card, but the response is lost (timeout, network blip).
    3. Client never gets confirmation -> assumes failure -> retries the request.
    4. Without idempotency: customer gets charged TWICE.
    5. With idempotency: server recognizes the retry and returns the original result without charging again.

    You can't avoid retries (they're necessary for reliability), so you make the operation safe to repeat instead.


# Idempotent vs Non-Idempotent (by HTTP method, conceptually)
    Idempotent:
    - GET     -> reading data, no side effect
    - PUT     -> "set field X to value Y" -> repeating it keeps the same end state
    - DELETE  -> "delete resource X" -> deleting an already-deleted resource still results in it being gone
    
    NOT idempotent by default:
    - POST    -> typically means "create a new thing" -> calling twice = two things created
    - PATCH   -> depends on semantics. "increment counter by 1" is NOT idempotent. "set status = done" IS idempotent.

    NOTE: This is about the *contract/semantics*, not a guarantee. A poorly implemented PUT can still have side effects (e.g. sending a notification on every PUT call).


# How to make an operation idempotent (Idempotency Keys)
    Most common technique for POST-like operations (payments, order creation, etc.)

    1. Client generates a unique "Idempotency-Key" (usually a UUID) BEFORE making the request.
    2. Client sends the key in the request header:
         Idempotency-Key: 7b1a9f3e-...
    3. Server, on receiving a request with a key:
         - Checks if this key has been seen before (lookup in DB/cache).
         - If NOT seen: process the request normally, store {key -> result, status} , return result.
         - If seen already:
             - If original request is still processing -> return 409/425 (in-progress) or block until done.
             - If original request completed -> return the SAME stored result, don't reprocess.
    4. Client reuses the SAME key when retrying the SAME logical request (e.g. on timeout). A new key = a new, different operation.


# Generating the Idempotency Key on the frontend
    Goal: one key per LOGICAL user action/intent, reused across all retries of that SAME action.

    1. Generate a random, unique value — usually a UUID v4.
         - Browser: crypto.randomUUID()  (built-in, no library needed)
         - Fallback/older: uuid npm package -> uuidv4()
    2. Generate it ONCE, at the moment the user triggers the action (e.g. clicks "Pay Now"),
       NOT inside the fetch/axios call itself (else every retry would create a new key, defeating the purpose).
    3. Store that key somewhere it survives across retries of the SAME attempt:
         - React: useRef or component/form state (persists across re-renders, reset only when a NEW action starts).
         - Redux/global store: if the action can survive a page reload and still needs to be retried.
    4. Attach it to every retry request for that action:
         fetch('/api/payments', {
           method: 'POST',
           headers: { 'Idempotency-Key': key },
           body: JSON.stringify(payload)
         })
    5. Only generate a NEW key when the user starts a genuinely NEW action
       (e.g. clicking "Pay Now" again after a completed/failed payment, submitting a new order).
       Reusing the old key here would be wrong; discarding it as still "new" is also wrong — the key's
       lifetime = one logical business operation, from first attempt to final resolution (success or terminal failure).

    Example (React):
        function handlePay() {
          const idempotencyKeyRef = useRef(crypto.randomUUID()); // created once per checkout attempt
          const submit = () => fetch('/api/payments', {
            method: 'POST',
            headers: { 'Idempotency-Key': idempotencyKeyRef.current },
            body: JSON.stringify(order)
          });
          // retries (manual "try again" click, axios-retry, etc.) call submit() again with the SAME ref value
        }

    Why generate client-side instead of server-side?
    - If the server generated it, a lost response means the client never learns the key and can't retry safely
      (it would have to make a brand new request with a new server-generated key -> back to square one).
    - Client-side generation means the key exists BEFORE the network call, so it's available for every retry
      regardless of whether earlier responses were lost.


# Where to store idempotency records
    - A dedicated table/cache: (idempotency_key, request_hash, status, response_body, created_at)
    - request_hash: hash of the request payload, so if the same key is reused with a DIFFERENT payload, you can detect misuse and reject (409 Conflict) instead of silently returning stale data.
    - TTL/expiry: keys usually expire after some window (e.g. 24h) since retries won't happen forever.


# Handling concurrency (race condition)
    Problem: Two requests with the same idempotency key arrive at nearly the same time (client fired a retry before the first one finished).
    Solution:
    - Use a DB unique constraint on idempotency_key + atomic "insert if not exists".
    - First request wins the insert -> proceeds to process.
    - Second request's insert fails (duplicate key) -> it knows another request is in-flight -> waits/polls or returns "in progress".
    - This turns the check + store into a single atomic operation (avoids TOCTOU race).


# Idempotency at different layers
    1. Client-side: generate and persist the idempotency key before sending, so retries reuse it (don't regenerate per attempt).
    2. API/Application layer: idempotency key table as described above.
    3. Database layer: 
         - Unique constraints (e.g. unique order_id) to prevent duplicate rows.
         - Upserts (INSERT ... ON CONFLICT DO NOTHING/UPDATE) instead of blind INSERT.
    4. Messaging/Queues:
         - Consumers should be idempotent because most queues offer "at-least-once" delivery (a message can be delivered more than once).
         - Common pattern: track processed message IDs (dedup table) and skip if already processed.


# Idempotency vs Exactly-Once
    - True "exactly-once" delivery/processing across a distributed system is effectively impossible to guarantee end-to-end.
    - What we actually build is: "at-least-once delivery" + "idempotent processing" = effectively-once behavior from the user's perspective.


# Real world examples
    - Stripe/payment APIs: require an Idempotency-Key header on POST /charges.
    - REST resource design: PUT /users/123 {name: "Ankit"} -> safe to retry.
    - Kafka consumers: dedup using message offset/ID before applying business logic.
    - Database migrations: scripts written as "CREATE TABLE IF NOT EXISTS" so re-running them is safe.


# Quick summary
    Idempotent = same request repeated any number of times -> system ends up in the same state as if it were applied once.
    Achieved via: idempotency keys, unique constraints, upserts, dedup tables, atomic check-and-insert.
    Needed because: retries are unavoidable in distributed systems, and you want retries to be safe, not harmful.
